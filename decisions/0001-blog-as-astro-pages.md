# 0001. ブログ記事は Markdown ではなく1本ずつの .astro ページとして書く

- Date: 2026-08-03
- Status: Accepted

## Context

ポートフォリオに `/blog` を作るにあたって、記事の持ち方を決める必要があった。

このブログの目的は「自前でソースを持っているからこそできる、リッチな図表・アニメーション表現」
を使った記事を書くこと。Zenn などの外部サービスでは表現できないものを置く場所にしたい。
つまり、記事ごとに独自の SVG・CSS アニメーション・スクリプトを書けることが最優先の要件になる。

候補は3つあった。

1. Astro の content collections + Markdown
2. content collections + MDX（`@astrojs/mdx` を追加）
3. 記事1本 = `src/pages/blog/{id}.astro` の手書きページ

1 は表現力が足りない。2 は本文中にコンポーネントを埋め込めるが、
記事固有の `<style>` や `<script>` を書くには結局コンポーネントに切り出す必要があり、
「その記事だけの実験的な表現」をやるには一段遠い。

## Decision

**3 を採る。記事1本 = 1つの `.astro` ページ。**

そのうえで、一覧・絞り込みに必要なメタデータ（タイトル・日付・カテゴリ・draft）は
`src/data/blog.ts` を唯一の情報源とする「レジストリ方式」で持つ。

- 記事ページは自分の id で `getPost(id)` を引き、`BlogArticle` レイアウトに渡す
- `/blog` と `/blog/category/{id}` は **`src/data/blog.ts` だけ** を読む

メタデータを記事ファイル側から `import.meta.glob('./blog/*.astro', { eager: true })` で
集める方法も検討したが採らなかった。一覧ページが全記事コンポーネントを import することになり、
**記事ごとに書いた `<script>` が一覧ページのバンドルに巻き込まれる**ためである。
レジストリ方式ならこれが構造的に起きない（ビルド後の HTML で確認済み: `/blog` に記事側の
スクリプトは入らず、記事ページにフィルタのスクリプトは入らない）。

記事内で使う図表コンポーネント（`src/components/blog/`）は外部ライブラリを使わず、
インラインの HTML / CSS / SVG で書く。静的サイトにランタイム JS を増やさないため。
アニメーションは `Layout.astro` に既にある `.reveal` の IntersectionObserver に相乗りする。

## Consequences

**楽になったこと**

- 記事ごとに `<style>` `<script>` SVG を何の制約もなく書ける。表現の実験がそのまま記事になる
- 依存が増えない（MDX も remark プラグインもチャートライブラリも入っていない）
- 一覧・カテゴリページのペイロードが記事本数に影響されない

**諦めた / 代償**

- 記事を1本書くたびに **2ファイル**（レジストリ + ページ）を触る必要がある
- 片方だけ足して忘れる事故が起きうる → `src/data/blog.structure.test.ts` で
  「`src/pages/blog/*.astro` のファイル名集合」と「レジストリの id 集合」の一致を検証し、
  ズレたら CI が落ちるようにした。日付形式・カテゴリの妥当性も同じテストで見ている
- 本文がプレーンな Markdown ではないので、他所への転載は手作業になる

**再検討すべきタイミング**

- 記事が20本を超えたとき（2ファイル編集の負担と、レジストリの見通しが問題になり始める頃）
- 「書くこと」が主目的の記事が増えて、表現の自由度より執筆速度が欲しくなったとき
  → その時点で content collections + MDX への移行を検討する。メタデータは既に
  構造化されているので、frontmatter への移行自体は機械的にできるはず
